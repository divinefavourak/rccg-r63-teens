# SEO audit — 11 November 2026

**Site:** <https://www.thefaithtribe.live>
**App (iPhone web app):** <https://app.thefaithtribe.live>
**Auditor:** engineering review of the code, the production build and the live
responses. No paid rank-tracking or backlink tool was used.

---

## The short version

The code in this repository already has a stronger technical SEO foundation than
most small sites ever get: one real HTML file per route, correct canonicals,
per-page titles and descriptions, Open Graph and Twitter cards, JSON-LD,
a sitemap with real `lastmod` dates, an RSS feed, `llms.txt`, a considered
`robots.txt`, responsive AVIF/WebP images, and a build that refuses to ship
duplicate titles or canonicals.

The largest SEO problem is not missing code. **The production site is not serving
this code.** The live site still canonicalises every URL to `/`, still gives every
devotional the home page's title, and still points its sitemap at the host that
redirects to `www`. Until that is deployed, almost nothing else on this list can
work, because Google is being told that all 136 URLs are the home page.

After the deploy, the biggest remaining gains are, in order:

1. pre-rendering the body of content pages (not only the `<head>`);
2. giving the 123 devotionals permanent archive/tag/related links;
3. creating real pages for manuals and media, with transcripts and schema;
4. building authority (backlinks, local listings, social profiles).

## P0 — fix now

### 1. Deploy the current work, then verify production

The live site is an older deployment. This is the single highest-impact action.

Evidence from the live site:

```text
$ curl -sL https://www.thefaithtribe.live/ | grep canonical
<link rel="canonical" href="https://thefaithtribe.live/" />

$ curl -sL https://www.thefaithtribe.live/devotionals/38b72a41-... | grep -E '<title>|canonical'
<title>RCCG Region 63 Teens — Faith Tribe</title>
<link rel="canonical" href="https://thefaithtribe.live/" />
```

Every devotional and event URL tells Google it is a duplicate of `/`. In that
state, the archive cannot rank, no matter how good the copy is.

After deploying, run:

```bash
curl -s https://www.thefaithtribe.live/robots.txt          # Sitemap must be www
curl -s https://www.thefaithtribe.live/sitemap.xml | head   # <loc> must be www

# Take the first real devotional URL from the sitemap, not a placeholder.
ID=$(curl -s https://www.thefaithtribe.live/sitemap.xml \
  | grep -o 'https://www.thefaithtribe.live/devotionals/[^<]*' \
  | head -1 | sed 's#.*/##')
curl -s "https://www.thefaithtribe.live/devotionals/$ID" \
  | grep -E '<title>|canonical|og:url'

# The fallback shell still returns 200; what matters is that it says noindex.
curl -s -D - https://www.thefaithtribe.live/no-such-page -o /tmp/unknown.html \
  | grep -iE 'HTTP/|x-robots-tag'
grep -i 'name="robots"' /tmp/unknown.html
```

Then in Google Search Console:

- submit `https://www.thefaithtribe.live/sitemap.xml`;
- open **Page indexing** and look for “Alternate page with proper canonical tag”;
- check **Enhancements** for Article, Event, FAQ and Breadcrumb;
- request indexing for the home page and the three newest devotionals.

### 2. Keep the app out of the index

`app.thefaithtribe.live` is the iPhone web app. It is a login-gated shell, not a
content site. Live, its `/robots.txt` returns the app's `index.html`, and its
`<head>` has no `robots` directive. That is a thin page competing with the
website for the brand name.

Fixed in this pass:

- `mobile/public/robots.txt` now disallows everything;
- `mobile/public/index.html` carries `<meta name="robots" content="noindex, nofollow">`;
- `mobile/vercel.json` sends `X-Robots-Tag: noindex, nofollow`.

### 3. Stop made-up URLs returning an indexable 200

The catch-all rewrite serves `app.html` for every unknown path. Before this
pass, that shell was indexable, so every typo and every stale link could become
a soft 404. `app.html` is now `noindex, follow`, with an `X-Robots-Tag` on the
file itself.

The remaining improvement is a real `404` status. Vercel can do this with a
`routes` entry that returns `status: 404` for paths that are not real files and
not one of the known SPA prefixes (`/dashboard`, `/admin`, `/console`,
`/coordinator`, `/payment`, `/ticket-*`). A real 404 is cleaner than a noindex
200 and keeps the crawl budget honest.

### 4. `llms.txt` was never published

`writeLlmsTxt()` existed in `scripts/generate-site.mjs` but was never called, so
`dist/llms.txt` did not exist even though the build describes one. It is now
written and checked. It lists the site's main pages and the 15 newest
devotionals for answer engines.

### 5. `npm run seo` could only run once

`generate-site.mjs` replaced the `seo:start` region inside `dist/index.html`.
A second run then found no region and failed. The script now keeps a pristine
copy of the built shell in `.seo-shell.html` (gitignored), so `npm run seo` is
repeatable without shipping a second HTML file.

## P1 — next 30 days

### 6. Pre-render the body, not just the head

The build writes correct `<head>` tags and a `<noscript>` summary for every
route, but the visible body is still an empty `<div id="root">` until React and
the API respond. Google can render JavaScript; many other crawlers and answer
engines do not. The page's best asset — the devotional text — is not in the HTML
a non-JS crawler receives.

Options, cheapest first:

1. **Add the devotional body to the list serializer** (`content` or a trimmed
   `excerpt`) and write it into the generated `<noscript>` block. This is a
   small API change and makes the text readable by every crawler. It does not
   fix the visible-first-paint problem.
2. **Prerender with a headless browser at build time** (`vite-plugin-prerender`,
   `prerenderer` + Puppeteer, or a small custom script). This produces a real
   body for each route and is the best fit for the existing Vite setup.
3. **Move the public site to SSR** (Next.js/Remix/Astro). The largest change,
   but it removes the class of problem permanently.

If only one is done this quarter, do (1) and then (2).

### 7. Give old devotionals links that are not the sitemap

There are 123 devotionals. The list page asks for 60; the sitemap lists 123.
That means roughly half the archive has no internal link. Add:

- **Monthly archives** — `/devotionals/2026/11`, `/devotionals/2026/10`, with a
  unique title (“Teenage Open Heavens — November 2026”) and a short intro.
- **Topic or tag pages** — `/devotionals/tag/prayer`, `/tag/purity`,
  `/tag/exams`, using the `tags` field the API already has.
- **Previous / next reading** on each devotional.
- **Related readings** at the foot of each devotional (same tag or nearby date).
- **A visible breadcrumb** on every content page (the JSON-LD exists; the
  visible trail helps users and reinforces the hierarchy).

Use path segments, not query strings, so each becomes a clean canonical URL.

### 8. Create pages for manuals and media

`/manuals` and `/media` are list pages. The individual PDFs and episodes have no
HTML page of their own, so they cannot rank, cannot be shared with a good card,
and cannot carry structured data.

- **Manuals:** one page per series/week with a summary, the memory verse, the
  teacher notes as text, a PDF download, and `LearningResource` schema.
- **Media:** one page per episode with a description, a transcript, an embed,
  and `VideoObject` or `PodcastEpisode` schema. Transcripts are the single
  highest-value text asset in a media library.
- **Events:** after each event, a recap page with the date, venue, photos and
  (with consent) a short testimony. It turns a one-day event into evergreen
  content and internal links.

### 9. Clean the scraped devotional titles

Some API titles arrive as `TOPIC – Don’t Respond With Hate`, and some repeat
month after month. The build already avoids duplicate `<title>` tags by adding
the date, but the raw title still reaches `llms.txt`, the Article `headline`,
the RSS feed and the page's visible heading.

Normalise at ingestion or in the build:

- strip a leading `TOPIC –`, `THEME –`, `OPEN HEAVENS` or similar label;
- trim trailing punctuation;
- title-case only where the source is shouting;
- keep the date in the `<title>` (already done).

Better titles raise click-through rate on results that are already ranking.

### 10. Add parent and leader landing pages

The people who install, pay for and recommend the app are parents and leaders.
The current site speaks mostly to teens. Add:

- **For parents** — what the app is, what data it collects, how safety and
  consent work, what it costs. This targets queries like “safe Christian app for
  teenagers”, “RCCG teen app for parents”.
- **For church leaders** — the Console, class lists, check-in, events and
  reports. This targets “church management software for RCCG”, “teen church
  attendance app”, and gives parishes a page to link to.

Link both from the footer and the help page. Use `FAQPage` schema on each.

### 11. Local SEO

The organization node now carries a city-level address
(`Lagos, Lagos, NG`). To win local and brand searches:

- create or claim a **Google Business Profile** for the Region 63 Junior Church
  location(s) that meet publicly;
- keep the name, address and phone identical everywhere (site footer, Google,
  Facebook, Instagram, YouTube);
- add a visible contact block with the phone and email to the footer or the help
  page;
- add `sameAs` links in `seo/site.mjs` once the church controls the social
  accounts (the field is ready and empty on purpose).

Do not invent a street address for a region that meets in many parishes. Use the
one public meeting point, if there is one.

### 12. Performance and Core Web Vitals

Measure before changing anything. Run Lighthouse on `/`, `/devotionals` and one
devotional page on a throttled mobile profile, or read the Core Web Vitals
report in Search Console after the deploy.

Known items from the code:

- The landing route downloads roughly 235 KB of gzipped JavaScript before it can
  paint (`react-vendor` 59 KB, app 53 KB, `motion` 40 KB, `site` 7.5 KB,
  `LandingPage` 10.7 KB, plus the shared chunk). That is acceptable on fast
  Wi-Fi and expensive on a low-end Android on mobile data.
- The hero `<h1>` animates from `opacity: 0` (`word` variant in
  `pages/landing/Hero.tsx`). The LCP text is therefore invisible until the
  animation starts. Animate transform and rotation but leave opacity at 1 so the
  headline paints immediately.
- The largest generated images are 200–342 KB at 2048px. Check that `sizes` on
  each `ResponsiveImage` matches the box it renders into; a wrong `sizes` makes
  the browser pick the 2048px file for a 300px card.
- `frontend/public/rdtce.png` is 562 KB and is not referenced anywhere. Remove
  it or move it out of `public/`.
- Two illustration SVGs are 200 KB and 209 KB (`clumsy`, `plant`). Minify them
  or export the largest as WebP if they are not interactive.

### 13. Finish the web manifest

`frontend/public/site.webmanifest` lists a 192px icon and a 180px Apple icon but
no 512px icon and no maskable icon. Add both, matching the app manifest. This is
not a ranking factor, but it improves install quality and the PWA experience the
site already promises.

## P2 — 30 to 90 days

### Content

- **A “Today” module on `/devotionals`.** Put today's reading first, with the
  date in the H1 area. The title already targets “Teenage Open Heavens”; the
  page should make the “today” intent obvious above the fold.
- **Topic clusters.** Group devotionals by the questions teenagers actually ask:
  exams, friendship, purity, anger, purpose, money, grief, identity. Each tag
  page gets a short editorial intro, not just a list.
- **A glossary.** “What is a memory verse?”, “What is a grace day?”, “What is
  Teenage Open Heavens?” — short definitions with links into the content.
- **A yearly review.** “What 123 devotionals and four camps looked like in 2026”
  — a linkable, shareable asset for the church and for parents.
- **Testimonies and stories** with written consent. These are the pages other
  churches and blogs will link to.

### Off-page

- Ask every Region 63 parish with a website to link to
  `https://www.thefaithtribe.live` from its youth page.
- Ask the RCCG regional and national youth pages to list the app.
- List the app in Christian directories and Nigerian family/parenting sites.
- Put the site link in every YouTube description, Instagram bio, Facebook page
  and WhatsApp community description.
- Pitch one story per quarter to a Christian youth publication: camp stories,
  teen reading habits, a profile of a teacher using the Console.
- Add `sameAs` links once those profiles exist.

### Measurement

- Verify the site in **Google Search Console** and **Bing Webmaster Tools**.
- Add **IndexNow** (a key file plus a ping after each deploy) so Bing and Yandex
  see new devotionals without waiting.
- Track a small keyword set monthly: “teenage open heavens today”, “RCCG teen
  devotional”, “daily devotional for teenagers”, “RCCG camp registration”,
  “Bible study manual for teenagers”, “Christian app for teenagers Nigeria”.
- Add conversion events in Vercel Analytics: sign-up, event registration,
  Android download, web-app install.
- Review Search Console monthly: impressions, CTR, average position, index
  coverage, Core Web Vitals, structured-data errors.

## Honest limits

- **No field Core Web Vitals.** The PageSpeed Insights API quota was exhausted
  during this audit. Use Search Console's CWV report or run Lighthouse locally.
- **No backlink data.** A meaningful backlink audit needs Ahrefs, Semrush or
  Majestic. Search Console's Links report is the free starting point.
- **Backend tests could not run here.** The test suite needs the local Postgres
  container and Docker was not running. `manage.py check` passes, the mobile
  typecheck passes, and the frontend builds; the frontend typecheck still has
  pre-existing errors in files untouched by this pass (legacy admin pages and
  services).
- **The live site was audited as it is today.** The repo's current build fixes
  most of the on-page findings; they only count once deployed.
